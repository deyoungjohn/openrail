# UI states checklist

Every screen in the web app (`services/web`) must show the same set of states, in both themes, and
work from the keyboard. This page lists each screen and the end-to-end test that proves each state,
so a reviewer can check a claim by running one test. Status: **built** and **tested** against the
fixture API and the mock API; nothing here was run against a real wallet or chain.

## What "done" means for a screen

| State                  | What the screen must do                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Loading                | Show a skeleton (never a blank page, never a spinner for content). A button that starts work shows a busy button. |
| Empty                  | Say what is missing and what to do next, in plain words.                                                          |
| Error                  | Say what happened and that nothing was changed or charged, and offer "Try again" when a retry helps.              |
| 360 px, light and dark | No horizontal scroll and no WCAG 2 A/AA violation (axe), in both themes.                                          |
| Keyboard               | Every control is reachable with Tab, shows the solid 2 px focus ring, and focus is never trapped.                 |

## How to check

- Run every proof: `pnpm --filter @openrail/web build`, then `pnpm --filter @openrail/web exec playwright test`.
- Run one screen: add the spec name, for example `... playwright test w5` (see the file names below).
- The table names the spec file and the test title. The shared checks for loading, keyboard, and the
  screens the per-screen specs do not cover are in `states.spec.ts`.
- To see a loading state by hand, delay the API answer: the test helper `mockApi` takes `delayMs`
  (`e2e/api-mock.ts`).

## Cross-cutting checks

| Check                                                 | Proof                                                                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| No shadow, glow or blur in either theme               | `noglow.spec.ts`                                                                                                          |
| Solid 2 px accent focus ring, 2 px offset             | `noglow.spec.ts`: "the focus ring is a solid 2px accent outline"; `states.spec.ts` keyboard checks the ring on every stop |
| Theme follows the system, no flash, choice remembered | `shell.spec.ts`                                                                                                           |
| No session token in web storage                       | `session.spec.ts`: "the page never keeps a session token in web storage"                                                  |
| The signed-in journey against the mock API            | `smoke.spec.ts`                                                                                                           |

## Known limits

- The keyboard check tabs through a page and checks the focus ring and that focus is not trapped. It
  does not check the logical order of every control; the sale form has an order test of its own.
- Loading is proved by holding an answer back. A very fast real API shows the skeleton only briefly.
- Reduced motion is handled in the stylesheet (`prefers-reduced-motion`) and is not asserted by a test.
- The tests run against fixtures and the mock API, not the live API.
